# 二、R2 必须修复的问题

## P0-1：CSV 初始化失败时没有阻止 CFST 执行

**问题位置：** `app/pipeline.py`，`pipeline.run_once()`。

当前代码逻辑存在以下风险：

```python
if auto_csv:
    cfst.prepare_run_csv(run_csv)
started_ns = time.time_ns()
```

`prepare_run_csv()` 有返回值，但调用方没有检查。

如果本轮独立 CSV 路径中存在旧文件，而清理操作因为权限或 I/O 错误失败，程序仍然可能继续执行 CFST。

随后新鲜度判断又存在时间容差，可能错误接受残留文件。

**整改要求：**

1. 必须检查 `prepare_run_csv()` 的返回结果。
2. 初始化失败必须立即终止本轮测速。
3. 不允许调用 CFST runner。
4. 六个 TXT 必须全部保持旧内容。
5. 正式历史 CSV 必须保持不变。
6. 运行状态必须记录明确失败原因。
7. 不得把初始化失败误记为普通测速失败或成功。

**必须新增测试：**

- 预先创建一个 mtime 很新的旧 CSV。
- 模拟清理失败。
- 确认 CFST runner 调用次数为 0。
- 确认六个旧 TXT 内容完全不变。
- 确认正式历史 CSV 完全不变。
- 确认状态中记录 CSV 初始化失败。

这是 R2 的最高优先级问题。

## P1-1：CSV 新鲜度判断不能只依赖 mtime 时间容差

**问题：**

R1 已测试：
- 本轮未生成 CSV。
- CSV 时间戳为 10 天前。
- CSV 不完整。

但尚未测试：
- 本轮独立路径中存在一个刚刚修改过的旧文件。
- 清理失败后，旧文件 mtime 仍然落在允许时间范围内。

**整改要求：**

1. 以本轮独立路径和运行前清理成功作为前置条件。
2. 清理失败必须 fail-closed。
3. 新鲜度判断不能单独依赖 mtime。
4. 必须证明本轮 CSV 是由本轮 CFST 实际生成的。
5. 对时间戳精度及文件系统行为给出合理说明。

不能因为旧文件时间比较新，就认为它属于本轮测速。

## P1-2：运行状态 JSON 没有真正写入磁盘

**问题位置：**
- `app/pipeline.py`
- `app/output.py`

目前：
- `pipeline.run_once()` 返回运行状态字典。
- `output.render_run_status()` 只负责生成 JSON 字符串。
- 尚未完成正式状态 JSON 文件的持久化。

**整改要求：**

实现：

- `data/result.json`
- `data/last_run.json`

建议采用：

1. 生成完整 JSON 内容。
2. 写入同目录临时文件。
3. flush。
4. fsync。
5. 回读或校验 JSON。
6. 使用 `os.replace()` 原子替换正式文件。
7. 清理失败遗留的临时文件。

两个文件的用途需要明确：

- `result.json`：本次运行的完整结果。
- `last_run.json`：最近一次运行状态，供后续监控、调度和推送读取。

必须说明两者是否保存相同数据，还是分别保存完整结果和轻量状态。

**状态至少应包含：**

- 运行时间、时区、运行模式。
- CFST 命令及退出码。
- CSV 是否新鲜、是否完整、记录数量。
- 有效 IP 数量。
- 最快节点及其速度、延迟。
- 六个 TXT 各自的更新状态。
- 每个文件的节点数量。
- 每个文件失败原因。
- 总体成功、失败或部分成功状态。
- 运行失败原因。

**安全要求：**

- JSON 中不得包含 Token、SendKey、密码或其他凭据。
- JSON 写入失败不得破坏已成功发布的 TXT。
- 状态写入失败必须能够记录并报告。
- 部分成功、全部成功、全部失败必须能够区分。

**必须新增测试：**

- 正常写入两个 JSON。
- JSON 原子替换成功。
- JSON 写入失败。
- JSON 替换失败。
- 状态文件旧版本保留。
- JSON 写入失败时六榜仍按各自结果处理。
- 不包含任何敏感凭据。
- 部分成功状态能够正确记录。

# 三、正式部署前必须完成的事项

以下事项不是要求 R2 全部实施，但必须纳入后续阶段计划，不能遗漏。

## P1-3：定时任务防重入机制尚未实现

**问题：**

产品需求要求每天北京时间 06:00、12:00、18:00 执行。

如果上一次完整测速尚未结束，下一次定时任务可能启动第二个实例。

**整改要求：**

在配置正式 Cron 之前实现防重入：

1. 使用可靠的进程锁或文件锁。
2. 同一时间只能存在一个运行实例。
3. 前次未结束时，新任务直接跳过。
4. 记录跳过原因和时间。
5. 异常退出后锁能够正确释放或恢复。
6. 不允许因残留锁文件导致永久无法运行。
7. 必须测试两个并发运行实例。

建议安排在正式调度阶段完成，但必须作为 Cron 上线前的验收条件。

## P1-4：容器环境尚未进行实际集成验证

**留待阶段 4.2。**

需要验证：

- Python 3.12 容器环境。
- UID 1000 / GID 0 非 root 运行。
- `data/`、`logs/` 目录实际读写权限。
- 0o600 TXT 是否能够被后续消费者读取。
- 只读根文件系统是否正常。
- tmpfs 是否正常。
- 容器重启后数据是否保留。
- 容器不加入 Mihomo 网络。
- 不设置 HTTP_PROXY / HTTPS_PROXY / ALL_PROXY。

特别注意：

0o600 的文件权限意味着只有文件所有者能够读取。必须验证未来提供订阅服务的 Web 服务、GitHub 上传程序及其他消费者是否具有正确的读取权限。

不得为了方便读取而直接放宽所有文件权限。

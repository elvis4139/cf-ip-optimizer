## 二、必须修复的六项问题

### R3-01：RunCsvInit 证据绑定（原 P1-1）

当前 `RunCsvInit.token` 生成后未参与 `csv_is_fresh()` 验证。

要求：

- 明确 token 的用途：必须用于绑定本轮初始化证据，不能只生成、不校验。
- `csv_is_fresh()` 必须确认传入的初始化证据与当前 CSV 路径、本轮运行上下文相符。
- 不允许把其他路径或其他运行产生的初始化对象作为当前生产 CSV 的有效证据。
- 如果实现中发现 token 无法可靠绑定运行上下文，可以调整证据对象结构，但不得降低生产路径的校验强度。
- 对缺失、错误、重复使用或路径不匹配的证据一律拒绝。

新增离线测试至少覆盖：

- 正确 token、正确路径、本轮证据：通过。
- token 缺失或不匹配：拒绝。
- 路径不匹配：拒绝。
- 使用其他运行的证据：拒绝。

### R3-02：source 严格白名单（原 P1-2）

当前只有 `source == "production"` 被识别为生产模式，其余值都进入宽松测试分支。

要求：

- 只允许两个明确值：
  - `production`
  - `test_explicit`
- 其他值，包括 `None`、空字符串、未知字符串，一律拒绝。
- `production` 必须满足生产证据要求，包括运行前文件不存在的证明。
- `test_explicit` 仅允许用于明确指定 CSV 路径的离线测试，不得被生产流程使用。
- 测试模式不得成为生产证据缺失时的自动回退路径。

新增测试覆盖：

- `production` 合法证据。
- `test_explicit` 合法离线路径。
- `None`、空字符串、未知 source 全部拒绝。
- 生产模式缺少 `pre_absent` 证据时拒绝。
- 生产流程不得调用 `test_explicit` 分支。

### R3-03：CSV freshness 文件系统异常 fail-closed（原 P1-3）

当前 `csv_is_fresh()` 中 `is_file()`、`stat()` 等操作可能抛出 `OSError`，而 `run_once()` 在调用该函数时没有完整异常保护。

要求：

- 对 CSV 文件检查过程中可能出现的文件系统异常进行明确捕获。
- 任何无法确认文件存在、类型、大小、时间戳或证据有效性的情况，都必须视为 freshness 验证失败。
- 失败必须进入统一 `_abort()` 路径。
- 不允许异常直接逃逸 `run_once()`，导致失败状态没有记录。
- freshness 失败时不得归档 CSV，不得更新六个 TXT。
- 原有正式 CSV 和六个 TXT 必须保持原样。

新增测试覆盖：

- `is_file()` 检查抛出 `OSError`。
- `stat()` 抛出 `OSError`。
- CSV 路径被删除或替换。
- freshness 验证失败后 `_abort()` 被调用。
- runner 已执行但 freshness 无法确认时，六榜均不得更新。

### R3-04：两个 JSON 状态文件独立持久化（原 P1-4）

当前 `publish_json_file()` 的父目录创建和临时文件创建发生在内部 `try` 之外；`_persist_status()` 又将两个文件的循环放在同一个异常边界中。

要求：

- `result.json` 与 `last_run.json` 必须各自拥有完整、独立的异常处理边界。
- 每个文件的父目录创建、临时文件创建、写入、fsync、回读、JSON 解析、凭据扫描、原子替换均须纳入各自的异常处理。
- 任意一个文件失败，不得阻止另一个文件继续尝试更新。
- 一个文件更新成功、另一个失败时，整体状态应明确记录为部分持久化失败。
- 保持现有原子写入原则：临时文件写入、校验成功后再 `os.replace()`。
- 单个文件失败时，不得破坏该文件旧版本。
- 临时文件清理失败也应被记录，不得掩盖原始错误。

新增测试覆盖：

- `result.json` 的 mkdir 失败，`last_run.json` 仍继续尝试。
- `result.json` 的 mkstemp 失败，`last_run.json` 仍继续尝试。
- `last_run.json` 的写入失败，`result.json` 正常更新。
- 单个文件 replace 失败，旧文件字节不变。
- 两个文件均失败时，分别记录各自失败原因。
- 两个文件均成功时，JSON 格式和原子替换检查通过。

### R3-05：Path.exists() 对断开符号链接的误判（原 P2-1）

当前 `prepare_run_csv()` 使用 `Path.exists()` 判断文件是否存在，无法可靠识别 broken symlink。

要求：

- 对生产 CSV 路径的目录项存在性检查，使用能够识别断开符号链接的方式，例如 `os.path.lexists()` 或 `lstat()`。
- 运行前只要存在同名目录项，包括普通文件、目录、符号链接、断开符号链接，都不能记录为 `pre_absent=True`。
- 对残留对象的清理必须遵循现有安全边界，不得递归删除目录，不得跟随符号链接删除其目标。
- 清理失败时必须 fail-closed，禁止启动 CFST。
- 不得误删正式 CSV、六个 TXT 或其他历史数据。

新增测试覆盖：

- 普通残留文件。
- 正常符号链接。
- 断开符号链接。
- 目录占用 CSV 路径。
- 清理失败时 runner 调用次数为 0。
- 清理成功后才允许进入后续生产流程。

### R3-06：凭据扫描大小写和边界补强（原 P2-2）

现有字段白名单机制继续保留，不重构 `build_result_payload()` 和 `build_last_run_payload()` 的整体数据结构。

要求：

- 保留 `_FULL_FIELDS`、`_LIGHT_FIELDS` 等字段白名单。
- 扩展凭据扫描，使常见标记检查不再依赖大小写完全一致。
- 覆盖 `TOKEN=`、`token=`、`SendKey`、`sendkey`、`Bearer `、`BEARER `、`github_pat_` 等大小写变体。
- 对常见密钥字段名和疑似凭据内容进行扫描。
- 不得将真实密钥写入测试输出、日志或报告。
- 不得为了测试而使用真实 GitHub PAT、Server 酱 SendKey 或其他真实凭据。
- 发现疑似凭据时，拒绝写入对应 JSON 文件，并记录不包含密钥原文的失败原因。

新增测试覆盖：

- 大小写变化的凭据标记。
- 常见 Bearer 标记变化。
- 常见 token、password、api_key 字段。
- 字段白名单之外的字段不会被序列化。
- 凭据扫描拒绝写入时，旧 JSON 文件保持不变。
- 错误信息不得回显疑似凭据原文。

## 三、增加一项明确的状态准确性修正

### R3-07：生产 CSV 归档失败不得报告 overall_status=success

R2 代码中，`overall_status_of()` 只看测速成功和六榜更新情况，CSV 归档失败仅追加 warning，可能导致生产任务在 `csv_archived=false` 时仍显示 `overall_status=success`。

本项明确纳入 R3，不允许自行忽略，也不允许借此扩大状态系统重构范围。

要求：

- 对生产模式，CSV 测速成功但正式 CSV 归档失败时，整体状态不得为 `success`。
- 应使用现有状态体系中最合适的 `partial` 或 `failed`，并保持状态语义一致。
- 必须记录 `csv_archived=false` 和具体失败原因。
- 归档失败不得触发六榜回滚或破坏已经成功原子更新的 TXT；保持现有单榜隔离语义。
- `test_explicit` 离线测试路径不要求正式 CSV 归档，因此不得仅因 `csv_archived=false` 就误判离线测试失败。
- 不得修改 CSV 测速参数、榜单排名规则或 TXT 格式。

新增测试覆盖：

- production 测速成功、六榜成功、CSV 归档成功：整体 success。
- production 测速成功、六榜成功、CSV 归档失败：不得 success。
- production 测速成功、部分榜单失败：维持原有 partial 语义。
- test_explicit 离线路径无归档：不因 `csv_archived=false` 被误判。

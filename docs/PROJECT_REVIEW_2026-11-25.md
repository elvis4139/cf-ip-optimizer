# Cloudflare IPv4 节点测速与 EdgeTunnel 订阅优化项目

**讨论整理日期：** 2026-11-25

## 1. 项目目标与范围

项目目标是建立一套运行在 QNAP NAS Docker 环境中的 Cloudflare IPv4 节点测速、质量评估、筛选和订阅文件生成流程，并将生成结果供 EdgeTunnel 使用。

本阶段重点是确定测量工具、正确理解已有实验数据、明确输出格式和数据处理边界。尚未确认的调度、阈值、分组和输出数量不应提前写死。

### 本阶段范围

- 以 CFST v2.3.5 作为主测速工具。
- 参考其他开源工具的测量方法和算法设计。
- 区分 TCP、TLS、HTTP、Trace/Colo、下载测速等不同测量维度。
- 形成 EdgeTunnel 可识别的订阅行格式。
- 明确原始数据留存、排序、失败保护和发布安全原则。

### 不在本阶段默认执行的事项

- 不因讨论而自动部署新容器或修改 NAS。
- 不自动启用定时任务、通知或外部发布。
- 不将历史仓库中的旧代码和旧参数视为最新规格。
- 不预设必须按国家/地区拆分为若干订阅文件。

### 2.3 EdgeTunnel 订阅格式

当前最新确认格式：

```text
IP:PORT#国家-网速-延迟-城市(可选)
```

示例：

```text
172.64.229.43:443#JP-63.21MB/s-94ms-Tokyo
172.64.229.43:443#JP-63.21MB/s-94ms
```

字段约定：

| 字段 | 约定 |
|---|---|
| IP:PORT | IPv4 地址与端口 |
| `#` | 半角井号，作为名称分隔符 |
| 国家/地区代码 | 使用可靠的国家/地区代码；未知时不得猜测 |
| 网速 | 下载速度，单位 MB/s；示例保留两位小数 |
| 延迟 | 毫秒，示例为整数 ms |
| 城市 | 可选英文城市名；没有可靠信息时省略 |

注意：

- 上述是订阅行格式，不代表已确认订阅文件数量或分组方式。
- 不应把旧格式 `IP:PORT-国家-网速-延迟` 或旧的 Colo/城市拼接格式继续当作当前格式。
- 排序应基于原始精度数据；仅在最终输出文本时格式化数值。
- 丢包率可用于内部质量过滤，但当前订阅行格式不显示丢包率。
- 国家或城市信息不可靠时应留空或省略，不得通过猜测补齐。

### 2.4 不预设输出文件数量

用户已明确纠正过“固定六个文件”的假设。当前**没有确认**必须输出 HK、JP、SG、KR、US 等地区文件，也没有确认每个文件的节点数或 Global 文件数量。

因此，文件数量、分组策略、文件名和每组节点数均列为待确认项，不得从旧方案中自动继承。

## 3. 工具静态分析与实验结论

本节记录截至 2026-11-25 的讨论和实验摘要。实验结论仅适用于对应测试条件，不应直接外推为工具在所有网络环境中的普遍性能。

### 3.1 CFST v2.3.5

在同一组 80 个 IPv4 候选、端口 443 的测试中，分别执行了 TCP 探测次数为 3 次和 10 次的测试。

已观察到：

- 两次测试的 CSV 均记录了相同的 41 个 IP。
- 3 次探测测试：这 41 条记录合计 103 次成功、123 次尝试；其中 23 条记录为 0% 丢包。
- 10 次探测测试：这 41 条记录合计 336 次成功、410 次尝试；其中 10 条记录为 0% 丢包。
- 10 次测试的 41 条记录丢包分布：0% 为 10 条、10% 为 11 条、20% 为 12 条、30% 为 5 条、40% 为 1 条、50% 为 2 条。
- 两次 CSV 中均未出现的其余 39 个候选 IP，其缺失原因尚不能仅凭 CSV 断定。

**统计口径限制：** 336/410 只代表 CSV 中这 41 个 IP 的记录，不代表 80 个候选 IP 的整体成功率。不能把未出现在 CSV 的 IP 未经验证地解释为 100% 丢包、必然超时或其他特定状态。

CFST 丢包字段是比例值，例如：

- `0.33` 表示 33%；
- `0.67` 表示 67%。

不能将其误读为 0.33% 或 0.67%。

#### 10 次探测测试中记录为 0% 丢包的节点

| IPv4 | 平均延迟 |
|---|---:|
| 162.159.8.164 | 95.96 ms |
| 108.162.198.172 | 104.34 ms |
| 104.27.18.246 | 163.45 ms |
| 104.25.229.3 | 166.13 ms |
| 104.24.231.69 | 168.61 ms |
| 104.25.187.203 | 173.76 ms |
| 104.16.251.207 | 224.39 ms |
| 104.16.2.79 | 235.09 ms |
| 104.17.156.230 | 247.87 ms |
| 104.16.233.37 | 257.19 ms |

这些是对应测试样本中的观测值，不代表固定可用节点清单或未来性能保证。

### 3.2 CFData / CFData-WEB

对 CFData-WEB v1.8.5 的静态分析和测试显示，它包含 TCP、HTTPing、Trace/Colo、relink 等功能，但这些测量维度不能混为一谈。

已观察到的实现/测试特征：

- TCPing 使用固定 3 次探测。
- HTTPing 是单次请求；其结果中的丢包字段可能固定返回 0，因此 HTTPing 显示“0% 丢包”不能证明 TCP 层没有丢包。
- relink 开关在两次测试中的结果集没有出现变化。
- 测试结果集中约有 37/80 个候选被记录；其中一次实验观察到 36 个成功、44 个失败。失败原因包括 TCP 失败、Trace 超时、连接重置和 HTTP 403 等不同情况。
- 有少数 CFST 可达的 IP 因 CFData 的 Trace 失败而没有进入其结果集。

因此：

1. Trace/Colo 失败不等于 TCP 不通。
2. HTTP 请求失败不等于 TCP 不通。
3. 未知 Colo 或地区信息不等于节点失败。
4. 不应把 Trace 成功设为 TCP 节点入选的硬性前提。
5. 应保留各维度的独立状态和错误原因。

### 3.3 其他开源项目的参考价值

静态分析中涉及的项目和思路包括：

| 项目/方向 | 可参考的思路 | 使用边界 |
|---|---|---|
| `gh-tt/cloudflare-scanner` | 多次 TCP 探测、成功率、下载表现 | 可参考重复探测和质量统计，不替代当前主工具决定 |
| `ip-optimizer` | 多轮稳定性、延迟/下载波动系数 | 可借鉴稳定性评估算法 |
| `CloudFlareScan` | Colo 映射、下载测速 | 其探测前提和 TCP 测试次数需结合源码理解 |
| `better-cloudflare-ip` | TCP、TLS、HTTP CF-RAY 等分阶段探测 | 可借鉴分层探测思想，不应直接照搬为完整排序器 |
| Cloudflare Speedtest | 持续吞吐测量思路 | 可参考下载测速的测量方法 |
| CFData / CFData-WEB | TCP、HTTP、Trace/Colo、relink 的组合实现 | 需防止将不同层级的失败混为一类 |

当前决定仍是：CFST v2.3.5 为主工具，其他工具作为算法与实现参考。

## 4. 测量数据与质量判断原则

建议将每个候选节点的原始测量结果分维度保存，而不是压缩成单一的“成功/失败”字段。

建议的数据维度：

| 维度 | 建议记录的信息 | 说明 |
|---|---|---|
| 节点标识 | IPv4、端口 | 当前项目只讨论 IPv4 输出 |
| TCP | 探测次数、成功次数、丢包比例、延迟统计 | 反映 TCP 可达性与稳定性 |
| TLS | 握手是否成功、耗时、错误原因 | 与 TCP 分开记录 |
| HTTP | 请求状态码、耗时、错误原因 | HTTP 403 不应直接归类为 TCP 不通 |
| Trace/Colo | 是否取得信息、Colo/地区字段、失败原因 | 用于辅助地理信息，不作为 TCP 成功的必要条件 |
| 下载测速 | 原始下载速度、测试 URL、测试字节数、耗时 | 排序时保留原始精度 |
| 地理信息 | 国家/地区、城市、数据来源、可信度 | 不可靠时不输出猜测值 |
| 运行元数据 | 运行时间、工具版本、参数、输入文件摘要 | 用于审计与复现 |

### 4.1 不同测量维度必须隔离

- TCP 成功但 Trace 失败：仍应保留 TCP 成功记录。
- TCP 成功但 HTTP 403：保留 TCP 成功，同时记录 HTTP 层异常。
- 地理信息缺失：标记未知，不视为节点不可用。
- 下载测速失败：记录为下载测速失败，不覆盖 TCP/TLS 的原始结果。

### 4.2 原始数据优先

建议保留原始 CSV/JSON 和每次运行的元数据，以便后续重新筛选、排序和复盘。

不要只保留最终订阅文本，因为格式化后的速度和延迟会损失精度，也无法完整解释节点为何入选或被排除。

## 5. 排序、过滤与稳定性评估

排序和过滤参数尚未形成完整的最终规格。当前可确定的原则：

- 排序使用原始精度数据，不使用已四舍五入的订阅文本。
- 下载速度、延迟、丢包率应作为独立指标。
- 丢包率可用于质量过滤；具体阈值仍待确认。
- 稳定性评估可参考多轮测试、成功率、延迟波动和下载速度波动。
- 地理信息只负责标注和分组，不应替代连通性判断。
- 对缺失记录应区分“工具未输出”“超时”“明确失败”和“数据解析错误”，不能直接混为一个状态。

尚未确认的参数包括：是否要求 0% 丢包、TCP 探测次数、下载测试次数、二次复测范围、稳定性窗口、延迟/速度阈值、最终节点数量和排序权重。

## 6. 生成与发布安全原则

后续实现时应采用防止半成品覆盖有效订阅的策略：

1. 每次运行使用独立临时工作目录。
2. 先检查测速进程退出状态。
3. 验证 CSV/JSON 文件存在、表头正确、记录可解析。
4. 区分完整结果、部分结果和失败结果。
5. 只有达到约定的数据完整性条件后，才允许生成正式输出。
6. 先写入临时文件，再通过原子替换更新目标文件。
7. 全量测速失败或关键数据不完整时，保留上一版有效订阅。
8. 若未来允许分文件独立更新，必须先明确哪些失败条件允许局部更新，避免不同文件之间出现不一致的运行批次。
9. 记录运行时间、工具版本、参数、输入候选摘要、输出摘要和失败原因。

以上为实现安全原则，不代表当前已经部署了这些机制。
